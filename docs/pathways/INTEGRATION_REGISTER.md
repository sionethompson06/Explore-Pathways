Unconfigured features return honest unavailable/request states; do not fake success." Concretely, until each row above is resolved:

## Phase 3B: Vercel Preview database runtime (in progress -- blocked on a hosted database, not on code)

**The four databases this application can ever be pointed at, kept explicitly distinct (never conflated):**

| Environment | `DEPLOYMENT_MODE` | Where it runs | State as of this entry |
|---|---|---|---|
| LOCAL | `LOCAL` (default) | This sandbox / a developer's own machine | `pathways_dev` -- a real local PostgreSQL 16.13 instance, fully migrated, used for `pnpm dev`. |
| TEST | n/a (test runner only, never read by `src/env.ts`) | GitHub Actions' disposable `postgres:16` service container, or a developer's local `pathways_test` | A real, disposable/local PostgreSQL instance used only by `pnpm test`/CI; never shared with LOCAL or PREVIEW data. |
| PREVIEW | `PREVIEW` | Vercel Preview deployments (this repository's branch previews) | **Currently a non-functional placeholder** (`postgresql://user:pass@localhost:5432/db`) -- there is no real database behind it. This is the subject of this Phase 3B entry. |
| LIVE | `LIVE` | A future real production deployment | **Does not exist.** No production domain, database, or `DEPLOYMENT_MODE=LIVE` environment has ever been created or activated at any phase. Nothing in this entry changes that. |

**Root cause:** the PREVIEW `DATABASE_URL` was set at Phase 0/1, before any route in the application made a real database call, with an explicit comment that it was an intentionally unreachable placeholder ("this preview never calls the database"). Phase 3 subsequently added real, DB-backed routes (`/discover`, `/discover/profile`, `/discover/report`); the placeholder was never revisited, so the first real write (`INSERT INTO discovery_session`) now fails at runtime with `connect ECONNREFUSED 127.0.0.1:5432` -- exactly what the owner reproduced testing the deployed Preview.

**What exists today:** no hosted, remotely-accessible PostgreSQL instance for PREVIEW use. This session's Vercel API access does not have permission to list or create marketplace integration configurations (`403 Forbidden` on every attempted call, including after being asked to try again), and there is no other exposed API path to provision a new marketplace database resource without a human completing Vercel's own dashboard consent flow. Per this repair's explicit instruction, no paid or free external database was purchased or provisioned without that authorization -- this is reported as a genuine blocker, not silently worked around.

**What was completed this entry, independent of that blocker:**
- **`src/env.ts` loopback-DATABASE_URL safeguard:** any non-`LOCAL` `DEPLOYMENT_MODE` (`PREVIEW` or `LIVE`) now refuses to start at all if `DATABASE_URL` resolves to `localhost`, `127.0.0.1`, or `::1` -- failing fast at startup with an actionable message instead of surfacing only at request time as an opaque `ECONNREFUSED`. `LOCAL` is unaffected (a developer's own machine legitimately runs Postgres on localhost). Covered by 7 new Vitest cases in `tests/env.test.ts` (LOCAL+localhost/127.0.0.1 allowed; PREVIEW+localhost/127.0.0.1/`::1` rejected; PREVIEW+remote accepted; LIVE+localhost rejected) plus 2 pre-existing fixture URLs corrected in `tests/env.test.ts`/`tests/session-config.test.ts` that incidentally used a loopback host under a non-LOCAL mode.
- **`app/discover/error.tsx`:** a route-scoped error boundary covering `/discover`, `/discover/profile`, and `/discover/report`. If the Discovery flow's own server-side work throws (a temporarily unreachable database being the expected case), this shows a calm, honest "Discovery Is Temporarily Unavailable -- please try again shortly" state with a Try Again button, instead of Next.js's generic "This page couldn't load." It never surfaces the underlying error's message, host, SQL, or any credential -- verified directly by pointing a local dev server at a genuinely unreachable port and confirming only the fixed neutral copy renders in the page body (the full SQL/error detail that appeared was in the *browser devtools console*, which Next.js's development mode intentionally surfaces for debugging and which does not happen in a production build -- Next's own documentation confirms a thrown Server Component/Action error's message is redacted to a generic message + digest in production, and both Preview and Production deployments always build in production mode).

**What remains blocked, and the smallest next step:** a real, remotely-accessible PostgreSQL connection string for PREVIEW use. The fastest paths, in order of speed: (1) the owner or another team member with Vercel dashboard access opens this project's **Storage** tab and connects a marketplace Postgres provider (Neon or Supabase both have a free tier and take about two minutes), then shares the resulting connection string; or (2) any other already-existing hosted Postgres instance the owner controls. Once a connection string is provided, the remaining Phase 3B steps (setting the PREVIEW env var, running all committed migrations against it, verifying the schema, running the real deployed end-to-end Discovery flow, and confirming from the database side that a session/draft/`ProfileRevision` were genuinely created) can proceed immediately -- none of it requires further code changes beyond what is already committed here.

**Security note:** no database credential, connection string, or secret appears anywhere in this document, in any commit, or in this repair's completion report, per this repair's explicit instruction.
