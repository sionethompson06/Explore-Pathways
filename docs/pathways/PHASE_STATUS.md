Fixed by importing `eslint-config-next`'s native flat-config export directly; `@eslint/eslintrc` was removed from devDependencies once unused.

- `types.ts` / `index.ts` — shared types and the barrel export.

**Schema — smallest safe, non-destructive change (no new table was needed):** `discoverySession` gained `draftAnswers` (jsonb, default `{}`), `draftQuestionBankVersion`, `draftInterestHint`, `draftUpdatedAt`; `profileRevision` gained `submissionIdempotencyKey` plus a **partial unique index** `profile_revision_session_idempotency_unique_idx` on `(discoverySessionId, submissionIdempotencyKey) WHERE submissionIdempotencyKey IS NOT NULL`. Migration `drizzle/0001_harsh_legion.sql` (5 `ALTER TABLE` + 1 `CREATE UNIQUE INDEX`), applied cleanly to both `pathways_dev` and `pathways_test`. A resume/edit position is never stored as its own column — it is always re-derived from `computeActiveFlow`/`computeProgress` over `draftAnswers`, which makes position/answer drift structurally impossible (documented in `DECISION_LOG.md` DEC-G1).

**Session/draft persistence (`src/server/discovery-draft.ts`, new):** reuses the existing Phase 1 guest-session infrastructure (`src/server/session.ts`, `DiscoverySession`/`ProfileRevision`/`StudentPathwayRecord`) — no parallel guest-identity mechanism. `startDiscoveryAction` is a real server action (POST via a form, never a GET side effect) that creates/resumes a session, sets the HttpOnly `pathways_guest_session` cookie, and redirects to `/discover/profile`. Draft answers are saved to `discoverySession.draftAnswers` on every commit — never to `localStorage`/`sessionStorage`/the URL — with a "Saving…"/"Saved"/"Couldn't save — Retry" indicator in `DiscoveryQuestionnaire.tsx`; a failed save keeps the in-memory answer, shows the error, and offers Retry rather than silently advancing.

**Idempotent submission (14-step, transactional, exactly per the specification):** `submitDiscoveryProfile()` loads the session by HttpOnly token, loads the draft, loads the canonical bank, recomputes grade band and active questions, validates every required active question and every answer against canonical allowed values, recomputes effective answers (ignoring hidden-branch answers), creates the `StudentPathwayRecord` if none exists, creates the `ProfileRevision`, links the session, stores the loaded `questionBankVersion`, and redirects to `/discover/report`. Idempotency uses a **deterministic content-hash key** (`sha256` of a canonicalized, recursively-key-sorted `{sessionId, questionBankVersion, rawAnswers}`) rather than a client-supplied nonce, enforced by the partial unique index above; a Postgres `SAVEPOINT` (a nested `tx.transaction()` around the INSERT) lets a unique-constraint conflict roll back just that insert while the outer transaction still runs the idempotent-replay `SELECT` (Postgres otherwise aborts the whole transaction on any statement error). Proven directly: submit → revision 1; a network-retry of the identical submission → still revision 1 (same row returned, confirmed by `discovery-draft.test.ts`'s "is idempotent" test and a dedicated `Promise.all([...3 concurrent submits])` case in `discovery-security.test.ts` asserting all three return the same `revisionId`); a later intentional edit with materially changed effective answers → revision 2 (`discovery-draft.test.ts`'s "an intentional edit and resubmit creates a genuinely new revision"). Documented in `DECISION_LOG.md` DEC-G3.

**Editable homepage-interest handoff:** an allowlisted `?interest=` marketing value (`athletics`→`ATHLETICS`, `flexible_schedule`→`SCHEDULE_FLEXIBILITY`, `homeschool_support`→`HOMESCHOOL`, `academic_challenge`→`ACADEMIC_ACCELERATION`, `different_environment`→`DIFFERENT_ENVIRONMENT`, `unsure`→`EXPLORING`) is carried into the session as `draftInterestHint` and shown as a **visual preselection** on the GOALS stage's `discovery_reasons` checkboxes only — it is never written into `draftAnswers.discovery_reasons` until the parent actually interacts with that control, confirmed by `discovery-draft.test.ts`'s "clears the interest hint once a real discovery_reasons answer is saved". The marketing interest is removed from the URL the moment the questionnaire session begins; no child-profile answer ever appears in a URL query parameter (verified by a dedicated Playwright + a manual `page.url()` assertion).

**UI (`app/discover/**`, `src/components/discovery/**`):** `app/discover/page.tsx` is the real entry point with the exact required copy ("DISCOVER" eyebrow, "Let's Start With What You're Hoping to Make Possible" heading, "START MY DISCOVERY"/"HOW PATHWAYS WORKS" CTAs, an explicit "Development preview — please use sample information only" notice). `app/discover/profile/page.tsx` is a Server Component that authenticates the guest session, loads the draft, resolves safe serializable question descriptors via `present.ts`, and passes server-action function references as props into the small `DiscoveryQuestionnaire` Client Component (which never imports the domain module or holds database credentials, and never decides final validity — only server actions do). `app/discover/report/page.tsx` is the protected Phase-3 completion placeholder: "Your Discovery Profile Is Complete," an explicit "the pathway recommendation and report experience is the next build stage — it is not enabled in this development version yet" statement, and a "Nothing here ranks schools, scores your student, or names a provider" line — no mocked recommendation, no raw-answer exposure, no public report URL (session-owner-only, private/no-store, `noindex`). Reopening a completed profile for editing loads its raw answers into a new editable draft context without ever mutating the existing `ProfileRevision`; only an explicit resubmission creates the next revision.

**Real bugs found and fixed during this phase (all self-identified via failing tests, not user-reported):**
1. **Stage auto-skip-ahead** — recomputing "current stage" from answer-completeness on every render (instead of treating the `?stage=` URL param as the sole source of truth once landed) caused the server's own notion of "current stage" to silently advance the instant a stage's last required field was saved, before the user clicked Continue — fixed by redirecting to an explicit `?stage=` URL immediately on any landing without one.
2. **Continue-button race** — gating the Continue button's `disabled` state on `useTransition()`'s `isPending` (which reflects any prior field's in-flight `router.refresh()`) could swallow a fast click during a brief window — fixed by never gating Continue's `disabled` state on an unrelated field's save-transition.
3. **Accessible-name leak** — `.option[data-checked="true"]::before { content: "✓" }` changed a checked control's accessible name (e.g. "Athletics" → "✓ Athletics"), breaking name-based lookups and presenting an unstable name to assistive tech — fixed by rendering the checkmark as a real `aria-hidden="true"` DOM node, never CSS-generated content on a naming element.
4. **Missing accessible name** — a lone `short_text`/`integer_or_unknown` control inside a `<fieldset><legend>` has no auto-generated accessible name (unlike grouped radio/checkbox options, which each get their own `<label>`) — fixed with a conditional `id` on the legend plus `aria-labelledby` on the control.
5. **Zod issue misclassification** — a multi-select cardinality violation (`too_big`) was falling through to a generic `INVALID_VALUE` classification instead of `TOO_MANY_SELECTIONS` — fixed by checking the issue code together with `input_type === "multi"` before the generic fallback.
